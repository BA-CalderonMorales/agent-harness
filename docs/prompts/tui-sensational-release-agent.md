# Agent-Harness TUI Sensational Release Mission

Your mission is to make the next release of agent-harness an exceptional,
dependable terminal toolbox for engineers, with Linux and Android/Termux
as first-class experiences.

Work in this repository. Inspect, reproduce, implement, test, and prepare
reviewable changes. A design proposal or an audit alone does not complete
the mission.

## Product intent

This is my personal engineering toolbox, built openly so other engineers
can understand it, adapt it, and plug in their own workflows.

I should be able to take it to a new machine, repository, or workplace and
feel immediately capable: compose comfortably, understand what the agent
is doing, control its actions, recover from interruptions, and resume work.

Bring the care associated with excellent terminal tools and the ownership
and approachable customization that I value in projects like OpenCode,
Zensical, and MkDocs. These are inspirations, not a request to clone their
appearance or introduce their architectures.

“Sensational” means coherent, responsive, legible, discoverable,
portable, and trustworthy throughout real work. Visual polish matters, but
so do editing, cancellation, permissions, persistence, recovery, and
performance.

## Operating contract

Read AGENTS.md and applicable local instructions before working. Preserve
unrelated work and personal settings.

Determine the current release state rather than assuming a version. Follow
the repository’s release/X.Y.Z branch convention, based on develop. Make
focused conventional commits when checks permit. Prepare the release for
review; do not merge, tag, publish, or deploy without authorization. Every
PR description must end with:

`Generated by Agent-Harness`

Use the existing architecture:

- `cmd/agent-harness`: application wiring and delegates
- `internal/interface/tui`: terminal interface
- `internal/agent`: live agent loop
- `internal/runtime`: providers and tools
- `internal/core`: shared configuration and state
- `internal/loop`: modular rewrite, not automatically the live path

Keep one concept per file, target the 400-line limit, and keep pure moves
separate from behavioral changes. Prefer existing extension points. Explain
before making major architectural changes.

Honor GitNexus requirements: impact analysis before symbol edits,
caller/process/risk reporting, and complete graph change analysis before
committing. Warn before HIGH/CRITICAL edits. UNKNOWN requires investigation;
an empty graph result is not proof of safety. Use the repository CLI
fallback when MCP is unavailable. Never bypass a required analysis gate
silently.

Proceed autonomously with ordinary implementation decisions. Ask only when
missing access, a consequential product choice, or authorization actually
blocks progress. Continue independent work while awaiting input.

## 1. Establish the truth

Inspect current source, tests, build scripts, CI, documentation, and Git
history. Verify documentation against the live implementation.

Make discovery incremental. Start with local instructions, baseline checks,
a short interface inventory, and live desktop/narrow-screen observations.
Once a consequential defect is confirmed and its relevant history, source,
and required impact analysis are understood, implement and verify it.
Continue the full audit as each journey comes into focus; reading every
reference is not a prerequisite for the first fix. If the baseline reveals
no defect, begin with the clearest evidenced interaction improvement.

Pay particular attention to:

- `docs/architecture.md`
- `docs/loop-architecture.md`
- `docs/conversation_flow.md`
- `docs/command-approval.md`
- `docs/edgecases.md` and `docs/parity.md`
- `docs/environment-variables.md` and `docs/install.md`
- `docs/termux_edge_cases.md`
- `docs/os/termux/ui_ux_fixes.md`
- `scripts/demo/` and the local vibe-loop skill

Some documentation references retired `internal/ui` or `internal/tui` paths
and recommends avoiding the Termux TUI. Treat these as historical claims to
verify, not the desired product contract.

Study prior fixes and their tests, including these history anchors when
available:

- `d39cbcb`: Sessions vanished on narrow mobile panes
- `d76fa22`: frame borders moved between tabs
- `6c7da44`: composer lost its first line at wrapping boundaries
- `5b849b5`: deferred refresh pulled scrolled-up users to the bottom
- `d663cde`: cancellation left frozen thinking UI
- `1902ff3` and `04ce061`: long-session cache thrashing

For each recurring failure family, record:
original symptom → attempted fix → invariant to preserve → remaining gap.

Do not infer that these defects still exist. Reproduce current behavior. Do
not remove previous fixes without understanding what they protect.

Capture baseline build/test results and observe the actual TUI before
changing its behavior. Maintain a compact local working ledger outside
release changes: findings, reproductions, decisions, evidence, and next
actions.

## 2. Define a coherent experience

After initial observation, write a short experience contract covering:

- visual hierarchy and consistent spacing
- focus, navigation, and editing modes
- responsive layout priorities
- status, errors, approvals, and recovery
- desktop and mobile interaction alternatives

Implement against that contract so fixes reinforce one another.

Prefer useful content over decorative chrome on small screens. Preserve
orientation: active view, editing state, pending decision, and a clear way
back. Essential actions must remain reachable when labels or panels collapse.

Keep powerful keyboard workflows, with discoverable alternatives for people
who do not know Vim. Mobile essentials must not require obscure modifier
chords or a hardware keyboard.

Design quality is a release requirement. The experience contract must make
these qualities observable in actual use:

- Clear hierarchy: the draft, response, or pending decision is easy to find;
  supporting status and decoration leave it adequate space.
- Comfortable density: desktop space is useful, phone content remains
  legible, and resizing preserves focus and access to essential actions.
- Discoverable control: hints match the current context, common actions are
  reachable, and normal text entry does not require shortcut workarounds.
- Consistent presentation: spacing, emphasis, terminology, and interaction
  conventions agree across views and loading, error, and recovery states.
- Stable continuity: streaming, overlays, tab changes, and recovery preserve
  the user's reading position and explain changes of state.

Early in implementation, demonstrate two connected workflows at desktop and
phone dimensions: compose a multiline draft → approve a harmless tool task →
inspect its result; and read earlier output during a stream → cancel → reopen
the session. Record friction, unnecessary actions, and visual distractions.
Revisit these same workflows as fixes land and at final acceptance. Preserve
interactions that already meet the contract; a redesign is not required.

Use terminal captures or recordings for visual evidence where available;
plain text captures alone cannot establish color, contrast, or motion quality.
Share the early demonstration for optional maintainer steering and continue
independent work. Incorporate feedback when received; label unreviewed
subjective judgments honestly without treating silence as acceptance.

## 3. Audit complete user journeys

Inventory every reachable screen, overlay, picker, and significant state.
Audit these journeys end to end:

### First use and portability

Fresh setup, existing setup, project changes, unavailable provider, invalid
credentials, and updating without losing user configuration.

### Composition

Single and multiline drafts; typing through wrap boundaries; moving the
cursor; deleting; history recall; long pasted text; bracketed paste; Unicode,
combining characters, and wide glyphs; literal shortcut characters; sending
versus inserting a newline.

### Navigation

Every tab, command palette, model picker, settings, sessions, logs, help,
and modal. Check focus entry, movement, selection, dismissal, and return to
the previous context. Verify displayed hints match actual behavior.

### Active work

Slow streaming, long pauses, interleaved prose and tools, tool bursts, large
output, empty output, errors, cancellation, and a subsequent turn. Progress
must reflect real state. Final output and exported session order must agree.
A render failure must never silently become a blank screen.

### Control and trust

Approvals must explain the action and relevant scope, keep the full decision
accessible on narrow screens, and make approve/deny/cancel clear. Never make
interaction easier by weakening permissions. Test the real approval flow; an
auto-approved demo is insufficient.

### Reading and continuity

Scroll back while streaming, return to live output deliberately, inspect tool
details, copy/export, reopen sessions, restart, and resume after interruption.
Preserve drafts, user intent, and truthful execution state. Never replay a
potentially side-effecting tool merely to hide a disconnect.

### Customization

Verify existing provider/model, persona, tool, skill, and appearance
extension points as applicable. Persist choices consistently and document how
another engineer can make the toolbox their own using current APIs. Do not
create a new plugin framework just for this release.

## 4. Make Linux and Termux first-class

Use a practical terminal matrix:

- desktop: 120x32 and 160x48
- compact desktop: 80x24
- phone portrait: 40x24 and 50x30
- keyboard-reduced height: 40x12
- boundary stress: 30x10
- live transitions between narrow, wide, tall, and short sizes

These are starting fixtures, not claims about particular devices. Test direct
terminals and tmux where available. Exercise resizing while editing,
streaming, scrolling, and deciding an approval.

At extreme sizes, provide a usable compact state or a clear size message
with a recovery path. Never panic, lose drafts, hide an approval decision, or
trap the user.

Measure terminal cells, not bytes or rune counts. Account for ANSI styling,
borders, padding, wide characters, and truncation. Verify hit targets against
rendered positions. Clipping must not conceal essential controls.

Check Linux behavior with ordinary keyboard input and available mouse,
selection, and clipboard paths. Check reduced color and missing clipboard
support; meaning must remain understandable without color alone.

For Termux, distinguish:

- running natively on Android
- using Termux to SSH into a Linux host
- using either through tmux

Check soft-keyboard opening/closing, portrait/landscape changes, paste,
touch/scroll behavior, limited modifier access, background/resume, and network
interruption. Prefer capability and viewport handling over scattered
platform-name conditionals.

Inspect shell resolution, writable temporary directories, PATH, executable
locations, config/state storage, and available external commands. Do not
assume `/tmp`, `/bin/bash`, `sudo`, `systemd`, or desktop clipboard utilities.

Use environment-appropriate temporary paths. Do not change HOME globally or
modify real user configuration to make a demo pass.

A narrow Linux pane or `TERMUX_VERSION` override is simulation evidence.
Neither proves native Termux support. A cross-build is not a device test.

If no Android device is available, finish all independent work and provide a
short exact device-validation procedure, expected results, and remaining
uncertainties. Mark native validation pending; do not claim full acceptance.

“Take it anywhere” means portable setup and reliable local continuity. Do not
invent cloud sync or promise seamless cross-device sessions that the
implementation does not support.

## 5. Fix through a reproducible loop

For every finding:
reproduce → trace event/state/render path → assess impact → fix the cause →
test the invariant → observe the same interaction live again.

Rank findings:

- P0: data loss, unauthorized execution, crash, unrecoverable state
- P1: blocked task, inaccessible control, misleading execution state
- P2: recurring friction, poor readability, layout instability, lag
- P3: discretionary embellishment beyond the experience contract

Address P0/P1 first, then recurring P2 issues. Apply the experience contract
throughout each fix. Problems with hierarchy, density, discoverability, or
continuity belong at the severity their user impact warrants; do not defer
them as cosmetic work merely because the application passes its tests.
Audit all surfaces even when the first obvious defect is easy to fix.

Work in waves with at most two interaction areas under active modification.
Close each wave with appropriate regression checks, live workflow evidence,
and an updated ledger of remaining findings before expanding implementation.
Investigations can continue alongside a wave; a blocked area can be parked
with a precise resume point. Wave completion is a checkpoint, not release
completion. Continue through the full acceptance gates without arbitrary
commit quotas or automatic scope reduction.

Use the existing mock server and real TUI harness for deterministic work:

- `scripts/demo/mock-llm.py`
- `scripts/demo/demo-boot.sh`
- `scripts/demo/drive_tui.py`

Read scripts before using them. The demo pins provider and permissions; it
does not cover onboarding or approval behavior by itself. The burst20 fixture
exercises real tool calls: use an isolated disposable workspace. Start only
processes you own and clean up only those processes.

Use a real PTY/tmux terminal. Piping the interactive application is not a
valid live TUI test. Capture intermediate streaming states, not just the
finished response. Verify actual composer text before submitting simulated
keystrokes.

Extend deterministic fixtures for missing failure cases where useful. Do not
require paid inference for routine regression coverage.

Write meaningful behavior regressions and property/boundary tests where they
protect invariants. Do not approve changed snapshots automatically: a test
can preserve the wrong behavior. Explain intentional UX changes.

Measure long-session responsiveness and resource use using repeatable
fixtures and recorded hardware/environment. Set concrete performance budgets
from the baseline before optimizing. Check input, resize, scrolling, stream
rendering, idle CPU, and memory growth. Avoid unbounded caches and background
work that wastes mobile battery.

## 6. Recover from blockers without spinning

When something fails, classify it: application defect, existing baseline
failure, stale index, missing dependency, unavailable device, network/access
restriction, or harness bug.

Record the exact command and error. After repeated identical failures, change
the hypothesis or method rather than retrying indefinitely. Use supported local
fallbacks and documented setup. Request required permissions instead of
circumventing them.

Never delete indexes, relax checks, replace expected results, upgrade major
dependencies, or disable features merely to obtain green output.

If one dependency is blocked, continue unrelated verified work. Leave a
precise unblock instruction. Keep checkpoints sufficient for another agent to
resume without repeating discovery.

## 7. Release acceptance

Before declaring the release ready:

- Every inventoried surface and journey has an explicit audit outcome.
- All discovered P0/P1 issues are fixed and verified.
- Recurring P2 issues are resolved or explicitly presented for acceptance;
  do not silently downgrade them to finish.
- Relevant historical regressions remain covered.
- The terminal matrix has recorded outcomes and honest coverage gaps.
- Actual Termux testing is completed or clearly remains a release gate.
- Changed behavior has live before/after evidence.
- The experience contract is supported by the repeated desktop and phone
  workflows, with concrete evidence of resolved friction and coherent design.
  Record maintainer feedback and any subjective review still pending.
- Long-session behavior has measured results.
- Documentation matches current behavior and includes concise Linux, Termux,
  recovery, and customization instructions.
- Run appropriate targeted tests, then `go test ./...`, `go test -race ./...`,
  `go vet ./...`, `make build`, `make verify`, and other applicable CI checks.
- Attribute pre-existing failures against a baseline; do not call a failing
  gate green.
- Complete required GitNexus change analysis; partial/truncated results are
  unresolved.
- Keep scratch ledgers, personal state, credentials, and temporary captures
  out of release commits.

Conclude with:

1. Concrete improvements to everyday engineering work.
2. Focused commits and verification results.
3. Before/after evidence with terminal dimensions and environment.
4. Remaining defects, device gaps, and release blockers.
5. The repeated desktop-and-phone walkthrough, explaining how hierarchy,
   density, discoverability, and continuity meet the experience contract,
   with remaining subjective decisions for the maintainer’s assessment.

Do not claim every possible TUI defect is eliminated. Demonstrate a
systematic full pass over the defined scope and distinguish verified quality
from remaining uncertainty.

Begin by inspecting the checkout, reading local instructions, studying the
relevant history, and reproducing the current desktop and narrow-screen
experience. Then carry the implementation through the acceptance gates.
