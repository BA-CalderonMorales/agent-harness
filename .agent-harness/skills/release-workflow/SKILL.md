# Release Workflow Skill

> **Purpose:** the ship ritual for this repository, end to end.
> **Trigger:** "let's ship it", "ship it", "cut a release" — run this sequence.
> **Scope:** release/* branch flow, PR gates, version integrity, tag, CD babysitting.

The user owns this sequence. Run it in order, do not skip a gate, and never
merge on red or work around branch protection without being told to.

## Remote first

Every step drives the remote, and the remote is the only source of truth:
PRs carry the changes, remote CI is the gate, and remote CD builds and
publishes the release. Local git is a convenience for making the next push,
never an authority — a stale local `main` read 39 commits behind `origin/main`
during the 0.3.37 cycle, which is enough to compare branches backwards or tag
the wrong commit. Anchor state on `origin/*`, not on the working tree.

**A local version bump with a locally pushed tag that bypasses remote CD is a
last resort, not a route.** Only when CD is genuinely unavailable, and never
quietly: say so plainly, because the published artifacts then carry no CI build
provenance, no checksums from the pipeline, and no release record the workflow
can be audited against.

## Preconditions

Run these before touching the remote; all must pass.

```bash
go build ./... && go vet ./... && gofmt -l .
make verify                                        # structure + full test suite
./scripts/check-branch-name.sh release/X.Y.Z       # branch naming gate
./scripts/check-version-matches.sh X.Y.Z cmd/agent-harness/main.go   # tag gate
```

The version bump is its own commit on the release branch and carries the
changelog section: `chore(release): bump version to vX.Y.Z`, editing
`cmd/agent-harness/main.go` (`Version = "X.Y.Z"`) and `docs/changelog.md`.
A tag cut without it ships a binary reporting the old version — v0.3.25 and
v0.3.26 both shipped 0.3.24 this way, which is what the gate exists for.

## The sequence

**0. Open the release PR.** `release/X.Y.Z` → `develop`.

```bash
gh pr create --base develop --head release/X.Y.Z --title "Release vX.Y.Z" --body "..."
```

The body describes the changes and how to verify them, never references goal
files, task numbers or internal planning artifacts, and ends with the line
`Generated by Agent-Harness`.

**1. Address Copilot's review with specific commits.** One commit per comment,
each fixing that comment's issue. Copilot is **not guaranteed to appear** — it
reviewed #32 (four rounds) and #33 (one) but left nothing on #34 or #35. Its
reviews always land as `COMMENTED`, so they can block a merge via conversation
resolution but can never satisfy the required approval.

```bash
gh pr view <n> --json reviews,reviewRequests
gh api repos/:owner/:repo/pulls/<n>/comments     # inline threads
```

**2. Reply, then resolve.** Push the commit first, then reply on the thread
naming it, then resolve the thread — in that order, so the link is live.
`develop` has required conversation resolution on, so unresolved threads block
the merge independently of CI.

```bash
gh api repos/:owner/:repo/pulls/<n>/comments/<comment_id>/replies \
  -f body="Addressed in <sha>: <what changed>."
gh api graphql -f query='mutation($id:ID!){resolveReviewThread(input:{threadId:$id}){thread{isResolved}}}' -f id=<thread_id>
```

**3. Wait for CI green.**

```bash
gh pr checks <n> --watch --interval 15
```

Required checks on `develop` are `build`, `test`, `quality`; a PR also runs
`branch-naming`, `secrets`, `security`, `sbom` and the sharded tests.

**4. Merge to `develop`.** This is the gate that stalls: `develop` requires
**1 approving review**, the PR author cannot self-approve, and this session's
`gh` is authenticated as the author. `enforce_admins` is off, so an admin merge
works — but it bypasses protection the user configured, so ask which route they
want (`--admin`, a collaborator's approval, or relax-and-restore) rather than
choosing for them.

```bash
gh pr merge <n> --merge          # add --admin only with explicit consent
```

**5. Open `develop` → `main`.**

```bash
gh pr create --base main --head develop --title "Release vX.Y.Z: <summary>"
```

**6. Wait for CI green** on the second PR. A formality — `develop` and `main`
are near-identical — but not skippable.

**7. Merge into `main`.**

**8. Push the tag, derived from the branch name.** Tags are annotated and the
message matches the release PR title's summary.

```bash
# Fetch first, then tag the REMOTE's main. Tagging a local main can land
# the tag on the wrong commit when the local branch is stale, and the tag
# must point at the commit CI built and the develop -> main PR merged.
git fetch --tags origin
git rev-parse origin/main            # confirm it is the merge you just made
git tag -a vX.Y.Z origin/main -m "Release vX.Y.Z: <summary>"
git push origin vX.Y.Z
```

The pre-push hook validates semver, and `release.yml` refuses to build if the
tag does not equal `main.go`'s version. CD on the remote does the building,
checksumming and publishing — do not reproduce any of that locally.

**9. Babysit CD until the release actually lands.** Six platform binaries plus
`checksums.txt`.

```bash
gh run list --workflow=release.yml --limit 3
gh run watch <run_id>
gh release view vX.Y.Z
```

**10. Sync local branches.** Always fetch before comparing topology.
`main` drifts stale locally — it was 39 commits behind `origin/main` during the
0.3.37 cycle, which made the graph read backwards.

```bash
git checkout develop && git pull origin develop
git checkout main && git pull origin main
```

**11. Prune merged branches.** Dry run first, per `docs/branch-protection.md`.
Never `main` or `develop`; never an unmerged branch.

```bash
./scripts/prune-branches.sh --dry-run
./scripts/prune-branches.sh
```

**12. Cut the next branch** off `develop`. Patch by default; minor or major only
when the user says so.

```bash
git checkout develop && git pull origin develop
git checkout -b release/X.Y.Z+1
```

**13. Report what landed** — commits, PR links, tag, release URL — and what
should be worked on next.

## Traps

- **`scripts/release.sh` and `scripts/release/publish.sh` are superseded. Do
  not use them for this flow.** They assume the old develop→main direct flow
  and push straight to `develop` and `main`, bypassing the release branch,
  the branch-naming gate, PR review and CI. `check-remote.sh` and
  `bump-version.sh` remain useful.
- **`make release` cannot validate a pending release.** It runs
  `check-remote.sh`, which requires the code version to equal the latest remote
  tag — true only *before* the bump. Expect it to fail mid-cycle by design.
- **Never use `git describe --tags` to find the latest release** on `develop`:
  it returns the newest tag *reachable from HEAD*, and tags land on `main`. Use
  `git ls-remote --tags origin` (what the scripts do).
- **Branch names are exactly `release/X.Y.Z`.** No suffixes — `release/0.3.26-tui-polish`
  is what broke version integrity for 0.3.25/0.3.26. Enforced by
  `.githooks/pre-push` and the CI `branch-naming` job.
- **`docs/branch-protection.md` is out of date**: it lists required reviews as
  optional, but `develop` requires one.

## Version format

| Bump | When | Example |
|------|------|---------|
| patch | Bug fixes, tests, DX hardening (the default) | v0.3.37 → v0.3.38 |
| minor | New features | v0.3.37 → v0.4.0 |
| major | Breaking changes | v0.3.37 → v1.0.0 |

## Files

| File | Purpose |
|------|---------|
| `.githooks/pre-push` | Branch-name and tag-semver gate |
| `scripts/check-branch-name.sh` | `release/X.Y.Z` naming gate (also run by CI) |
| `scripts/check-version-matches.sh` | Tag must equal `main.go` version |
| `scripts/release/check-remote.sh` | Remote tag sanity check (pre-bump only) |
| `.github/workflows/ci.yml` | Build, vet, sharded tests, quality, security |
| `.github/workflows/release.yml` | CD on tag push: six platform binaries + checksums |
| `cmd/agent-harness/main.go` | Source of truth for the code version |
| `docs/changelog.md` | Release history, one section per version |
| `scripts/prune-branches.sh` | Prune merged branches (`--dry-run` first) |
